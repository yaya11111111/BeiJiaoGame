## 1. 玩家反馈（FR-14）

### 1.1 E 已经这样调用

```ts
await cloudApi.call('feedback.submit', {
  category: 'bug' | 'stuck' | 'suggestion' | 'newmode',
  content: '玩家填的说明（已 trim，5–300 字）',
  screenshotFileId: 'cloud://.../feedback/xxx.jpg',   // 没传截图就是 ''
  context: {
    levelId: 'L05',            // 没进关卡就是 ''
    levelTitle: '第 5 关 · 学四餐厅',
    mode: 'solo' | 'duo' | '', // 没选模式就是 ''
    viewId: 'A' | 'B' | '',    // 只有双人模式才非空
    page: 'settings' | 'result' | 'room',
    roomCode: 'AB3K9Q',        // 不在房间就是 ''
    submittedAt: 1764662400000 // 客户端毫秒时间戳
  },
  clientVersion: '0.2.0'
});
```

成功时期望返回 `data`：

```ts
{ feedbackId: string, createdAt: number }
```

失败按现有信封返回 `ok:false` + `code` + `message`。E 会把 `message` 原样显示在表单下方，
**并保留玩家已填的内容**，方便直接重试。

### 1.2 建议的落库结构（`feedbacks` 集合）

| 字段 | 类型 | 说明 |
|---|---|---|
| `_openid` | string | 服务端从上下文取，不信任客户端 |
| `category` | string | bug / stuck / suggestion / newmode |
| `content` | string | 5–300 字，服务端再校验一次 |
| `screenshotFileId` | string | 可空；云存储 `feedback/` 目录 |
| `levelId` / `levelTitle` | string | 可空 |
| `mode` / `viewId` | string | 可空；单人时 viewId 为空 |
| `page` | string | 来源页 |
| `roomCode` | string | 可空 |
| `clientVersion` | string | 版本排查用 |
| `submittedAt` | number | 客户端时间，仅参考 |
| `createdAt` | number | 服务端 `Date.now()`，统计以它为准 |
| `status` | string | 默认 `open`，后台处理后可置 `triaged` / `fixed` / `closed` |

索引建议：`createdAt` 倒序；`category`；`levelId`。

### 1.3 可选：状态回显

如果要做「我的反馈」列表，E 需要：

```ts
cloudApi.call('feedback.list', { limit: 20 }) // 只返回当前 openid 的
// → { list: [{ feedbackId, category, contentPreview, screenshotFileId, levelId, createdAt, status }] }
```

没有这个接口时，E 用本地最近 3 条回执显示「已提交 / 失败」，不影响主流程。

## 3. 双人关卡保存与恢复（FR-15）

### 3.1 分工

- **C**：保存房间级的关卡快照、暂停倒计时、恢复时校验房间与轮次。
- **D**：产出/接收局内快照（线索、道具、已完成操作、错误次数、解谜阶段、剩余时间）。
- **E**：保存/退出入口、恢复提示与流程（已实现，见下）。

### 3.2 E 现在存了什么

双人关卡中途退出时，E 在本地存：

```ts
interface DuoSessionSnapshot {
  roomCode: string;
  levelId: string;
  viewId: 'A' | 'B';
  elapsedSec: number;    // 已用时
  roomStartedAt: number; // 保存时房间快照的 startedAt，用于判断同一轮
  savedAt: number;
  progress?: Record<string, unknown>; // 预留给 D 的局内快照，现在不写
}
```

恢复时 E 调用 D 的挂载参数：

```ts
mountLevel({
  levelId, playMode: 'duo', roomCode,
  initialView: session.viewId,
  // 用已用时反推：倒计时从上次的位置接着走
  startedAtMs: Date.now() - session.elapsedSec * 1000,
});
```

**这只恢复了关卡、视角、计时。** 线索 / 道具 / 操作 / 错误次数 / 阶段需要 D 的快照，
以及 C 的云端保存（换设备、双方先后回房都要能拿到）。

### 3.3 希望 C 提供

## 6. 双人房间聚合同步与自适应降频（待 C / D / E 联调）

当前并没有 `room.sync`：E 在房间/结算页分别调用 `room.state`（约 0.5 秒）和
`room.heartbeat`（约 10 秒），D 在关卡内调用 `event.pull`（约 1 秒）。三者不能仅在
E 侧合并，因为关卡挂载后事件序号和应用回调由 D 持有，房间快照及在线状态由 C 定义。

### 6.1 建议接口（C 先冻结协议）

```ts
cloudApi.call('room.sync', {
  code: 'AB3K9Q',
  sinceSeq: 42,          // 首次/重连从上次已处理的位置继续；不能默认跳到最新
  levelId: 'L01',       // 不在关卡时可省略；服务端按需筛选关卡事件
});
// → {
//   room: RoomSnapshot, // 含 status、levelId、players、isHost、myViewId、startedAt、serverNow
//   events: RoomEvent[], // seq 升序，至多一页；不能跳过中间事件
//   lastSeq: number,     // 本页最后一条事件的 seq；空页等于 sinceSeq
//   hasMore: boolean     // true 时客户端立即补拉下一页
// }
```

服务端在同一调用中更新调用者的 `lastSeenAt` 并生成在线状态快照，避免独立的
`heartbeat` 与 `state` 对 `players` 数组并发读改写。只返回当前房间成员可见的事件；
`closed` 必须可识别，不能让客户端因鉴权错误而无限留在房间页。明确 `room.sync` 的
最大响应条数、空页 `lastSeq`、超时与错误码，并在 `server/API.md`、`server/README.md`
同步记录部署和索引要求。上线前保留旧接口，双方迁移完成后再移除。

### 6.2 客户端责任（D / E）

- D：局内 `LevelSync` 使用聚合响应中的 `events` 和 `lastSeq`，保持本轮 `start`、
  `close`、`result` 的边界及断线补拉；停止/卸载后忽略在途响应，不能重放旧局事件。
- E：房间、结算页改用同一个房间同步调度器，按快照更新玩家、选关和开局状态；
  切入关卡时交接 `sinceSeq`，关卡退出后接回。不要让 E 与 D 同时启动两个定时器。
- 调度：有新事件或玩家/房间状态变化时维持 1–2 秒；连续几次空响应后降到 4–5 秒；
  开局、回前台、重连及发送本地操作后立即同步。每房间最多一个在途请求，
  `hasMore` 时先补页再进入下一轮。若要求文字消息 1 秒内收到，静默降频期间需要
  推送唤醒或调整 US04 的时延验收标准，不能同时承诺固定 1 秒与 5 秒轮询。
- 验收：双机建房/入房、选关/开局、断线补拉、20 次重复进出、房主退出、
  前后台切换；记录每分钟请求数、最大并发、消息延迟、JS 内存与双方视角事件序号。

1. `snapshot` 的 `_id` 只含 `roomCode_levelId_openid`，重复开同关会覆盖旧轮；请加

`room.sync` 聚合与自适应降频不在这份 C 草案内，仍按第 6 节单独讨论。首版应优先
保证房间、事件和心跳正确，不能把静默 5 秒轮询同时宣称为 1 秒消息送达。
